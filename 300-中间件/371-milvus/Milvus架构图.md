### 核心思想：分布式、解耦、可扩展

在深入细节之前，首先要理解 Milvus 架构的设计哲学：​**将不同的职责（读写、查询、元数据管理、存储）分配给专门的、可独立扩展的组件**。这种“存算分离”和“读写分离”的架构，使其能够轻松应对海量向量数据的高并发写入和查询需求。

---

### 各层组件与名词详解（按照数据流从左到右）

#### 1. 客户端层

- ​**Client SDK（客户端软件开发工具包）​**​：
    
    - ​**意义**​：这是用户与 Milvus 数据库交互的入口。它不是一个数据库组件，而是一套封装好的编程接口。
        
    - ​**功能**​：开发者使用 Python、Java、Go 等语言的 SDK，可以方便地执行插入数据、创建索引、进行向量检索等操作，而无需关心底层的网络通信和协议细节。
        
    

#### 2. 无状态接入层

- ​**Proxy（代理节点）​**​：
    
    - ​**意义**​：系统的门户和流量调度器。它是无状态的，意味着可以轻松部署多个实例来实现负载均衡和高可用。
        
    - ​**功能**​：
        
        1. ​**接收请求**​：接收所有来自 Client SDK 的请求。
            
        2. ​**请求路由**​：根据请求类型，将其智能地分发给后端的特定组件。图中清晰地展示了这种路由：
            
            - ​**DCL/DDL**​ 请求（如创建集合、修改权限）交给 ​**Coordinator**。
                
            - ​**DML**​ 请求（如插入、删除、更新数据）交给 ​**Streaming Nodes**。
                
            - ​**DQL**​ 请求（即搜索和查询）交给 ​**Query Nodes**。
                
            
        
    - ​**知识点：DCL， DDL， DML， DQL**​（SQL语言的子集）
        
        - ​**DDL（数据定义语言）​**​：用于定义和修改数据库结构，例如 `CREATE COLLECTION`（创建集合）、`DROP INDEX`（删除索引）。
            
        - ​**DCL（数据控制语言）​**​：用于控制访问权限，例如 `GRANT`（授权）、`REVOKE`（收回权限）。
            
        - ​**DML（数据操作语言）​**​：用于对数据进行增删改，例如 `INSERT`（插入向量）、`UPSERT`（更新插入）。
            
        - ​**DQL（数据查询语言）​**​：用于查询数据，在 Milvus 中特指 `SEARCH`（向量相似性搜索）。
            
        
    

#### 3. 系统大脑与协调层

- ​**Coordinator（协调器）​**​：
    
    - ​**意义**​：整个集群的“大脑”，负责管理和协调工作，确保所有组件步调一致。它本身不存储用户数据，只存储元数据。
        
    - ​**功能**​：
        
        - ​**服务发现**​：记录所有 Worker 节点（Data Node, Query Node等）的状态和地址，让 Proxy 知道该把请求发给谁。
            
        - ​**元数据管理**​：管理数据库的“目录”，例如集合（Collection）的模式（Schema）、索引（Index）信息、数据分片（Sharding）情况等。
            
        - ​**负载均衡**​：监控各节点负载，在新数据到来时决定将其分配到哪个 Data Node。
            
        
    

#### 4. 工作者节点层（执行具体任务的核心）

这是架构中最核心的部分，体现了“职责分离”。

- ​**Workers（工作节点）​**​：一个统称，指所有实际干活的节点。
    
    - ​**Streaming Nodes（流节点）​**​：
        
        - ​**意义**​：数据库的“实时消息总线”，负责处理持续流入的增量数据。
            
        - ​**功能**​：接收来自 Proxy 的 DML 请求，将这些数据变更（插入、删除）以日志的形式快速追加到持久化层的 ​**WAL**​ 中，保证数据不丢失。它为后续的 Data Node 和 Query Node 提供实时数据流。
            
        
    - ​**Data Nodes（数据节点）​**​：
        
        - ​**意义**​：负责数据的持久化、压缩和索引构建。可以理解为“后台数据处理工人”。
            
        - ​**功能**​：
            
            1. 从 ​**WAL**​ 中读取流式数据。
                
            2. 将数据在本地进行**压缩（Compaction）​**，合并小文件以提高效率。
                
            3. 为数据段（Segment）​**构建索引（Indexing）​**，这是实现高速向量检索的关键。
                
            4. 将处理好的数据段（含索引）持久化到**对象存储**中。
                
            5. 将数据段的元信息（如位置、索引类型）通知给 Coordinator。
                
            
        
    - ​**Query Nodes（查询节点）​**​：
        
        - ​**意义**​：专门负责处理用户查询请求。可以理解为“前台服务人员”。
            
        - ​**功能**​：
            
            1. 从 Coordinator 获知需要加载哪些数据段。
                
            2. 从**对象存储**中加载数据段（Segment）到自身内存中。
                
            3. 接收来自 Proxy 的搜索请求，在内存中执行快速的向量相似性计算，并返回结果。
                
            
        
    

#### 5. 持久化存储层

这一层确保数据的持久性和可靠性，是“存算分离”架构中的“存”的部分。

- ​**Durable Storage（持久化存储）​**​：
    
    - ​**Meta Storage（元存储）​**​：
        
        - ​**意义**​：存放系统元数据的数据库。图中标注为 ​**etcd**，这是一个高可用的键值存储系统。
            
        - ​**存放内容**​：集合结构、用户权限、节点状态、数据段位置信息等所有“关于数据的数据”。
            
        
    - ​**WAL（预写日志）​**​：
        
        - ​**意义**​：系统的“流水账”。它支持如 ​**Pulsar、Kafka**​ 等消息队列。
            
        - ​**工作原理**​：在任何数据变更被应用到持久化存储（对象存储）​**之前**，都会先作为一条日志记录追加到 WAL 中。这样即使系统崩溃，也能从 WAL 中恢复数据，确保数据不丢失。
            
        
    - ​**Object Storage（对象存储）​**​：
        
        - ​**意义**​：海量向量数据的最终“仓库”。成本低、容量无限、可靠性高。
            
        - ​**常见实现**​：​**MinIO**​（自建私有云）、**Amazon S3**、**Azure Blob Storage**、**Google Cloud Storage**​ 等。

### 核心知识点串联：一次数据写入与查询的流程

1. ​**写入流程**​：
    
    - 用户通过 ​**Client SDK**​ 发起插入请求。
        
    - ​**Proxy**​ 接收到这个 DML 请求，将其转发给一个 ​**Streaming Node**。
        
    - ​**Streaming Node**​ 将插入操作作为一条日志记录，快速追加到 ​**WAL**​ 中，并返回成功响应给用户。此时数据已保证不丢失。
        
    - 后台的 ​**Data Node**​ 持续监听 WAL，读取到新的插入记录。
        
    - ​**Data Node**​ 将数据打包成段（Segment），进行压缩，并为其构建索引（如 IVF_PQ, HNSW 等）。
        
    - ​**Data Node**​ 将构建好索引的完整数据段上传到 ​**Object Storage**，并通知 ​**Coordinator**​ 该数据段已就绪。
        
    
2. ​**查询流程**​：
    
    - 用户通过 ​**Client SDK**​ 发起搜索请求。
        
    - ​**Proxy**​ 接收到这个 DQL 请求，将其转发给一个 ​**Query Node**。
        
    - ​**Query Node**​ 从 ​**Coordinator**​ 处得知需要加载哪些数据段。
        
    - ​**Query Node**​ 将这些数据段（含索引）从 ​**Object Storage**​ 加载到自己的内存中。
        
    - ​**Query Node**​ 在内存中利用索引进行高效的相似性搜索，计算出最相似的结果，通过 Proxy 返回给用户。
        
    

### 总结

这张架构图完美诠释了 Milvus 作为现代向量数据库的核心优势：

- ​**弹性扩展**​：每类节点（Proxy, Query Node, Data Node）都可以独立水平扩展，按需分配资源。
    
- ​**高可用性**​：无状态组件（Proxy）和多副本机制确保单点故障不影响整体服务。
    
- ​**高性价比**​：计算（Worker节点）和存储（对象存储）分离，计算资源可以按查询压力弹性伸缩，而数据则存储在廉价、可靠的对象存储中。
