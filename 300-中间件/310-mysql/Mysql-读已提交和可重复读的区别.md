MySQL 中的 ​`READ COMMITTED`（读已提交）​  和 ​ `REPEATABLE READ`（可重复读）​ 是两个重要的事务隔离级别。它们主要区别在于如何处理事务执行过程中其他并发事务对数据的修改是否可见、是否能解决“不可重复读”和“幻读”问题，以及它们的实现机制（主要是 MVCC - 多版本并发控制）。

以下是它们之间的核心区别：

1. ​不可重复读 (Non-repeatable Read)​​
    - ​定义：​​ 在同一个事务内，两次相同的查询（`SELECT`）操作，由于其他并发事务提交了修改（UPDATE 或 DELETE），导致这两次查询返回的数据行内容发生了变化（UPDATE）或某些行消失了（DELETE）。
    - ​`READ COMMITTED`：`会出现不可重复读`。
        - 在事务中第一次`SELECT`之后，另一个事务修改了某些数据并成功提交。
        - 在同一个事务内第二次执行相同的`SELECT`语句时，它会看到其他事务已提交的修改，因此可能返回不同的结果（值改变或行消失）。
    - ​`REPEATABLE READ`：`解决了不可重复读`。​​
        - 在事务中第一次`SELECT`之后，另一个事务即使修改了某些数据并提交了，在该事务后续的`SELECT`操作中（直到事务结束），它看到的永远是第一次`SELECT`时那个时间点的数据快照。其他事务提交的修改对该事务是不可见的。

2. ​幻读 (Phantom Read)​​
    - ​定义：​​ 在同一个事务内，两次执行相同的范围查询（如 `WHERE age BETWEEN 20 AND 30`），由于其他并发事务插入（INSERT）或删除了满足查询条件的行并提交，导致第二次查询返回了之前没有看到的额外行（像幻影一样出现）或之前存在的行消失了。
    - ​`READ COMMITTED`：`会出现幻读`。​​
        - 范围查询只保证看到的行是符合条件且已提交的，但其他事务可以在两次查询之间插入或删除满足条件的新行。如果这些事务提交了，第二次查询就可能看到新行（幻影行）或发现某些行不见了。
    - ​`REPEATABLE READ` (`仅限InnoDB`)：`在MySQL的InnoDB引擎下，解决了大部分幻读`。​​
        - ​注意：​​ _根据 SQL 标准_，`REPEATABLE READ` 隔离级别是允许出现幻读的。​但是，*InnoDB 引擎通过其 MVCC 实现和`Next-Key Locking`（间隙锁 + 记录锁）机制，在绝大多数只读查询场景下避免了幻读。​​
        - InnoDB 的 `REPEATABLE READ` 创建一致性快照时，不仅记录已存在行的值，还会记录查询当时符合条件行的范围。
        - 当其他事务尝试在快照事务的活动范围内插入新行时（例如`INSERT`一个满足之前查询条件的行），`REPEATABLE READ` 事务中的后续范围查询仍然只会看到第一次查询时的那些行（不会看到新插入的行）。
        - ​例外 (当前读)：​​ 如果事务内部执行了 `SELECT ... FOR UPDATE` 或 `SELECT ... LOCK IN SHARE MODE`（称为“当前读”），或者执行了 `UPDATE`/`DELETE`语句，并且这些操作恰好影响了一个范围，而在这个范围间隙内插入了新行，这时锁机制可能会锁住间隙阻止插入，或者如果插入发生在其他事务（且提交），本事务的当前读`有可能`看到新插入的行（如果它刚好满足本事务的修改/锁定范围的条件）。严格来说，这种情况在 SQL 定义中属于幻读（在本事务内两次范围查询结果不同）。不过，通过锁机制，InnoDB 的 `REPEATABLE READ` 能够阻止其他事务的插入或者确保本事务能看到并处理这些新行（通常通过锁冲突将其阻塞或使其失败），从而在业务逻辑上避免了意外的幻读。​所以通常我们说 InnoDB 的 `REPEATABLE READ` 解决了幻读。​​
3. ​数据可见性规则 (核心是 MVCC 快照的创建时机)​​
    - ​`READ COMMITTED`：​​
        - 每次执行 `SELECT` 语句时，都会创建一个新的最新一致性读视图（快照）。
        - ​因此，它能看到所有在本次 `SELECT` _开始前_已经提交的其他事务的修改。​​
        - 同一个事务内的不同 `SELECT` 语句，看到的数据可能不同（基于它们各自执行时点之前的已提交数据）。
    - ​`REPEATABLE READ`：​​
        - 只在事务中第一次执行 `SELECT` 或 `SELECT ... FOR UPDATE/SHARE` 等触发快照创建的操作时，创建一次一致性读视图（快照）。
        - 整个事务期间，​所有的一致性读都使用这个第一次创建的快照。
        - ​因此，在事务结束前，它只能看到该快照创建时点之前已提交的其他事务的修改。它看不到快照创建之后任何其他事务的提交（无论这些提交是在本事务的其他 `SELECT` 之前还是之后）。​​
        - 同一个事务内所有 `SELECT`（非当前读）看到的数据都是一致的，基于第一次快照的那个时间点。
4. ​锁机制​
    - ​`READ COMMITTED`：​​
        - 执行 `UPDATE`, `DELETE`, `SELECT FOR UPDATE/SHARE`（当前读）时，通常只对扫描到的实际存在的行加记录锁。
        - ​不加间隙锁 (Gap Locks)​。这可能会增加幻读的发生几率，但同时也减少了死锁的概率和对并发插入的限制。
    - ​`REPEATABLE READ`：​​
        - 执行 `UPDATE`, `DELETE`, `SELECT FOR UPDATE/SHARE`（当前读）时，除了对被扫描到的实际存在的行加记录锁，还会加间隙锁。
        - ​间隙锁 (Gap Locks)​​ 锁住的是索引记录之间的间隙，或者是第一个索引记录之前、最后一个索引记录之后的虚拟间隙。
        - 作用：​阻止其他事务在锁定范围内插入新行​（从而防止幻读）。这也意味着对范围的操作可能会锁住更大的区间，在高并发场景下可能增加死锁的概率和对并发插入的限制。

| ---------------------- | ----------------------------------------- | ----------------------------------------------- |
| ​脏读 (Dirty Read)​​ | 避免 (`NO`)                                 | 避免 (`NO`)                                       |
| ​不可重复读​            | ​发生​ (`YES`)                          | ​避免​ (`NO`)                                 |
| ​幻读​               | ​发生​ (`YES`)                          | ​在InnoDB中通过MVCC和锁机制通常避免（尤其是在只读查询时）​​ (`NO`) |
| ​一致性视图 (快照)​​      | ​每次 `SELECT` 创建一个新快照​                 | ​整个事务使用第一次 `SELECT` 时的快照​                   |
| ​其他事务提交后的数据可见性​    | ​可见​（提交发生在本次`SELECT`之前即可）             | ​不可见​（除非是当前读且有锁冲突）                          |

| ​常见应用场景​           | 大多数 OLTP 应用的默认或推荐级别（如 Oracle, SQL Server） | MySQL InnoDB 的默认隔离级别，需要强一致性或避免不可重复读的场景          |

​如何选择？​​

- ​`READ COMMITTED`​：如果你能接受同一个事务内两次查询可能看到不同结果（不可重复读），并且对高并发插入有要求（不介意或可通过业务逻辑处理幻读），这是一个性能较好且较常用的选择（尤其非MySQL数据库）。
- ​`REPEATABLE READ` (InnoDB 默认)​: 如果你要求同一个事务内多次读取相同记录必须得到一致的结果（解决不可重复读），并且在 MySQL InnoDB 下要求避免大多数幻读（尤其是基于快照的只读查询），同时能接受并发插入可能稍微受限或潜在的锁冲突/死锁稍多一点的风险（需处理好死锁重试），那么这个级别提供更强的数据一致性保证。这是 MySQL InnoDB 的默认设置。

理解这些区别对于设计和优化需要高并发的数据库应用程序至关重要。选择哪个级别取决于你的应用对数据一致性的具体要求和对并发性能的平衡考虑。

MySQL 中的 ​`READ COMMITTED`（读已提交）​​ 和 ​`REPEATABLE READ`（可重复读）​​ 是两个重要的事务隔离级别，它们主要解决并发事务中的数据一致性问题。以下是两者的核心区别：

---

### 🧾 1. ​不可重复读 (Non-repeatable Read)​​

- ​`READ COMMITTED`​  
    ❌ ​会出现不可重复读​：同一事务内两次相同的查询可能返回不同结果（因其他事务提交了 UPDATE 或 DELETE 操作）。
- ​`REPEATABLE READ`​  
    ✅ ​解决了不可重复读​：使用事务开始时的一致性快照，后续查询始终看到相同的数据快照，不受其他事务提交的影响。

---

### 👻 2. ​幻读 (Phantom Read)​​

- ​`READ COMMITTED`​  
    ❌ ​会出现幻读​：范围查询可能因其他事务插入新行而返回额外数据（如 WHERE 条件新增的记录）。
- ​`REPEATABLE READ`​（InnoDB 特有优化）  
    ✅ ​通常避免幻读​：通过 ​MVCC（多版本并发控制） + Next-Key Locking（间隙锁）​​ 锁住索引间隙，阻止范围内插入新行。例外：事务内执行 `FOR UPDATE` 或写操作时可能检测到新行。

---

### ⏱️ 3. ​数据可见性机制​

- ​`READ COMMITTED`​
    - 每次 `SELECT` 都会创建新快照，仅看到该查询前已提交的数据。
- ​`REPEATABLE READ`​
    - 仅在第一次查询时创建快照，整个事务中所有读取都基于此快照，无视后续其他事务的提交。

---

### 🔒 4. ​锁机制​

- ​`READ COMMITTED`​
    - ​仅锁实际存在的行​（记录锁），​不加间隙锁。
    - 优点：并发插入性能更高；缺点：幻读风险大。
- ​`REPEATABLE READ`​
    - 使用 ​Next-Key Locking​（记录锁 + 间隙锁），锁住索引记录及间隙。
    - 优点：避免幻读；缺点：可能增加死锁概率，限制并发插入。

---

### ⚖️ 5. 使用场景对比

|​特性​|`READ COMMITTED`|`REPEATABLE READ` (InnoDB)|
|---|---|---|
|​脏读​|避免 ✅|避免 ✅|
|​不可重复读​|发生 ❌|解决 ✅|
|​幻读​|发生 ❌|大部分解决 ✅（InnoDB优化）|
|​快照生成时机​|每次 SELECT 时创建|第一次 SELECT 时创建|
|​间隙锁​|不使用|使用（防止插入新行）|
|​适用场景​|高并发写入，容忍数据变化|需强一致性（如财务系统）|

---

### 💡 总结

- ​`READ COMMITTED`​：适合注重并发性能的场景（如实时数据展示），接受不可重复读和幻读的风险。
- ​`REPEATABLE READ`​（MySQL InnoDB ​默认级别）：提供更强一致性，尤其适合需事务内数据稳定的场景（如对账、统计）。依赖 InnoDB 的 MVCC 和间隙锁实现幻读防护。

> 📌 ​注意​：MySQL 的 `REPEATABLE READ` 通过技术优化超出 SQL 标准要求，实际中能解决大部分幻读问题。但在涉及 `FOR UPDATE` 等写操作时仍需谨慎。
